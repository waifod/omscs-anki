# Nelson, Welch & Ousterhout: everything not in the notes

Everything in the paper that the lecture notes do not state, plus the places where the paper contradicts them; validated against the paper text. The reference point is the lecture notes: the `distributed-file-systems.md` note now carries `> **Paper (Nelson et al.):**` callouts for the lecture-framing discrepancies listed under "Notes vs paper discrepancies", so some gaps below are now annotated in the note. Paper: <https://s3.amazonaws.com/content.udacity-data.com/courses/ud923/references/ud923-nelson-paper.pdf>.

This is Michael N. Nelson, Brent B. Welch, and John K. Ousterhout, "Caching in the Sprite Network File System", from the Computer Science Division, University of California, Berkeley. It appeared at SOSP in 1987 and in ACM Transactions on Computer Systems 6(1), February 1988. The "Nelson" here is Michael N. Nelson of the Sprite group, not Bruce Jay Nelson of the RPC papers (a Bruce Jay Nelson co-authored work, Birrell & Nelson's "Implementing Remote Procedure Calls", is a *cited reference* [BIRR84] because Sprite's kernel-to-kernel RPC uses a protocol similar to it; the two Nelsons are different people). Section numbers below are the paper's; page numbers are the printed page numbers the extraction preserves, counted from the title page as page 1.

## Abstract
- The one-sentence framing of the whole system: Sprite "uses large main-memory disk block caches to achieve high performance", with non-write-through caching on both client and server machines, a simple consistency mechanism that lets files be shared without stale data, and a file cache that negotiates with virtual memory over physical memory and changes size dynamically. (abstract, p. 1) [The file cache's negotiation with virtual memory over physical memory and its dynamic size are now stated in the note's Nelson callout (distributed-file-systems.md, section Sprite Distributed File System); the main-memory, non-write-through caching on clients and servers is not.]
- The three headline numbers, stated together in the abstract: client caches let diskless workstations perform within 0-12% of workstations with disks, client caching reduces server loading by 50%, and it reduces network traffic by 75%. The lecture gives the qualitative shape of these but not all three figures at once. (abstract, p. 1) [Now stated in the note's Nelson callout (distributed-file-systems.md, section Sprite Distributed File System) (0-12%, server load cut by a factor of two or more, network traffic cut by about a factor of four), so not beyond the notes.]

## Section 1: Introduction
- Why caching helps, stated as two distinct advantages: it reduces delays (a cached block is returned to a waiting process "five to ten times more quickly" than one fetched from disk) and it reduces contention for the disk arm when several processes access files on the same disk. (Section 1, p. 1)
- Prior timesharing measurements showed that even small caches give substantial benefits and that the benefit grows as physical memories grow [LEFF84, OUST85]. The lecture never cites the timesharing precedent. (Section 1, p. 1)
- Figure 1's data-flow model the lecture compresses: a file access is presented first to the local workstation's cache ("file traffic"); a miss goes either to the local disk if the file is stored there ("disk traffic") or to the server where the file is stored ("server traffic"); servers maintain their own caches to reduce their disk traffic. (Section 1, Figure 1, p. 2)
- On a machine with a disk the cache reduces disk delay and contention; on a client the cache additionally reduces communication delay, network contention, and server-machine contention. The lecture does not separate these per-role benefits. (Section 1, p. 2)
- The scalability argument from the literature: server CPUs appear to be the bottleneck in several existing network file systems [SATY85, LAZO86], so client caching offers greater system scalability as well as increased performance. (Section 1, p. 2)
- The paper names its own two "unusual aspects" explicitly: (1) a consistency guarantee even under simultaneous multi-client access to a cached file, giving "exactly the same semantics as if all of the processes on all of the workstations were executing on a single timesharing system"; (2) caches that vary in size dynamically. The lecture treats only consistency as the Sprite contribution. (Section 1, pp. 2-3) [That dynamic cache sizing is the paper's second contribution is now stated in the note's Nelson callout (distributed-file-systems.md, section Sprite Distributed File System); the single-timesharing-system semantics of the consistency guarantee is not.]
- The averaged speedup figure the lecture omits: client caching gave "a speedup of about 10-40%" for programs on diskless workstations relative to diskless workstations without client caches; server utilization dropped from about 5-18% per active client to about 1-9%; and from this the paper infers a single server should support at least 50 clients. (Section 1, p. 3)
- The comparison headline, stated up front: Sprite completed a file-intensive benchmark 30-35% faster than NFS and Andrew; Sprite's server utilization was substantially less than NFS but more than Andrew. (Section 1, p. 3)
- A full section-by-section roadmap of the paper (Sections 2-9). (Section 1, p. 3)

## Section 2: Overview of Sprite
- Sprite is a new OS built at Berkeley as part of SPUR, a high-performance multiprocessor workstation [HILL86]; the preliminary version ran on Sun-2 and Sun-3 workstations with about 1-2 MIPS and 4-16 MB of memory. The lecture gives none of this hardware context. (Section 2, pp. 3-4)
- The design target and its assumptions: future machines expected to have five to ten times the processing power and memory plus small degrees of multiprocessing; networks of up to a few hundred workstations; and, for economic and environmental reasons, most workstations will have no local disk, with large fast disks concentrated on a few servers. The diskless-by-design premise underlies the whole paper. (Section 2, p. 4)
- Sprite presents a UNIX-like interface [RITC74]: a single shared file hierarchy accessible equally from any workstation, name space managed as in [WELCH86a], and UNIX-like `open`/`close`/`read`/`write` system calls. (Section 2, p. 4)
- The kernel was completely re-implemented for network integration and is built around a kernel-to-kernel RPC facility [WELCH86b] using a protocol similar to Birrell & Nelson [BIRR84]; the file system uses RPC extensively for cache management. This is the only place "Nelson" (Bruce Jay) and "RPC" enter, and it is a dependency, not the subject. (Section 2, p. 4)

## Section 3: Background Work (the BSD study and server-contention motivation)
- The cache design's primary motivation was the "BSD study" [OUST85], a trace-driven analysis of file activity on several time-shared UNIX 4.2 BSD systems, which showed even small file caches cut disk traffic and large caches (4-16 MB) cut it "by as much as 90%". The lecture treats these numbers as if Sprite's own filesystem was traced; the paper is explicit they come from the earlier BSD timesharing study. (Section 3, p. 4) [The BSD-study provenance (time-shared 4.2 BSD systems, not Sprite) is now stated in the note's Nelson callout (distributed-file-systems.md, section Sprite DFS Access Pattern Analysis); the small- and large-cache traffic reductions (up to 90%) are not.]
- The BSD study's forward-looking inference: increasing memory sizes will soon make it possible to keep entire file working sets in main memory, with disks serving primarily as backup. (Section 3, p. 5)
- The explicit hypothesis-and-caveat the lecture drops: the BSD study was on timesharing machines, not networks of workstations, so the authors *hypothesized* the results would carry to a network and that remote-access overhead could be cut by caching on clients as well as servers; they point forward to Sections 5.3 and 7 for the simulation and measurement data meant to support the hypothesis. (Section 3, p. 5)
- The second motivation, server contention, with two independent sources: Lazowska et al. concluded the server CPU is the primary scalability bottleneck [LAZO86], and the Andrew designers independently redesigned their system to offload servers [SATY85] with substantial gains [HOWA87]. (Section 3, p. 5)

## Section 4: Basic Cache Design
- The section is framed around three explicit questions: where client caches should live (memory vs local disk), how caches should be structured and addressed, and what the write-back policy should be. Consistency and cache sizing are deferred to Sections 5 and 6. (Section 4, pp. 5-6)

### 4.1 Caches on Disk or in Main Memory?
- Prior network file systems (Andrew [SATY85, HOWA87], Cedar [SCHR85]) kept client caches on local disk; Sprite chose main memory for four reasons: (1) it permits diskless, hence cheaper and quieter, workstations; (2) data is accessed faster from memory than from a disk cache; (3) client memories are now large enough for high hit ratios (a 1-MB client cache gives >80% read hits); (4) server caches are in memory regardless, so using memory on clients too meant one caching mechanism for both. The lecture does not give the four-way rationale or the ">80% from 1 MB" figure. (Section 4.1, p. 6)

### 4.2 Cache Structure
- Caches are organized on a block basis with a fixed 4-KB block size, chosen "largely for simplicity" and explicitly provisional. The lecture does not give the block size. (Section 4.2, p. 6)
- Cache blocks are addressed *virtually*, by a unique file identifier (from the server) plus a block number within the file. The reason: virtual addresses let a client create new blocks in its cache without first contacting a server for their physical location, and let blocks be found without traversing the file's disk map. This virtual-vs-physical addressing choice is absent from the lecture. (Section 4.2, p. 6)
- A client caches only data blocks for remote files; servers additionally cache file maps and other disk-management information, addressed by physical disk address plus a special device "file identifier". (Section 4.2, p. 7)

### 4.3 Writing Policy
- The write-through baseline and its ceiling: write-through is reliable (little lost on a crash) but makes each write wait for disk, giving poor write performance; since about one-third of accesses are writes [OUST85], a write-through scheme "cannot reduce disk or server traffic by more than two-thirds". This is an upper bound on savings, which the lecture restates as a count of improvable operations. (Section 4.3, p. 7) [The two-thirds upper bound is now stated in the note's Nelson callout (distributed-file-systems.md, section Sprite DFS Access Pattern Analysis); write-through's reliability versus write-performance trade-off is not.]
- Delayed write-back has two advantages over write-through: writes complete quickly because they hit the cache, and data deleted before write-back need never be written at all; the BSD-study deletion statistics (20-30% of new data deleted within 30 s, 50% within 5 min) are what make delayed write-back pay off. The reliability cost is that unwritten data is lost on a crash. (Section 4.3, p. 7) [The BSD-study deletion statistics are now stated in the note body (distributed-file-systems.md, section Sprite DFS Access Pattern Analysis) and in the note's Nelson callout (distributed-file-systems.md, section Sprite DFS from Analysis to Design); the two advantages and the crash-loss cost are not.]
- Sprite's actual policy is "similar to the one used in UNIX": every 30 seconds, all dirty blocks not modified in the last 30 seconds are written back; a block written on a client reaches the server's cache in 30-60 s and the disk 30-60 s after that. The paper says it plans to experiment with longer intervals, so the trace argues for a *longer* delay, not for 30 s specifically. The lecture derives the 30 s interval from the 30 s deletion figure; the paper does not. (Section 4.3, p. 8) [Now stated in the note's Nelson callout (distributed-file-systems.md, section Sprite DFS from Analysis to Design), so not beyond the notes.]
- Write-on-close (used by Andrew and NFS) is rejected with the BSD open-duration data: 75% of files are open <0.5 s and 90% <10 s, so write-on-close would not significantly cut traffic; it also forces the closing process to wait for the write-through, undercutting the benefit of delayed writes. (Section 4.3, p. 8) [The rejection via the open-duration data is now stated in the note body and the note's Nelson callout (distributed-file-systems.md, section Sprite DFS Access Pattern Analysis); that write-on-close forces the closing process to wait is not.]

## Section 5: Cache Consistency
- The problem stated precisely: if a client modifies a file cached by others, can later references return stale data? Most existing systems give only limited guarantees. NFS and Andrew guarantee that once a file is *closed* all data is on the server and future opens by other clients pick up the new version; under "sequential write-sharing" (shared but never open for read and write on different clients at once) each client always sees the up-to-date version; but under "concurrent write-sharing" (open simultaneously on several clients with one modifying) the others do not see changes immediately, and users are warned off it. The lecture does not spell out this NFS/Andrew baseline or define the two write-sharing terms this way. (Section 5, pp. 8-9)
- Sprite's deliberately stronger choice: it permits *both* concurrent and sequential write-sharing and guarantees that any read returns the most recently written data regardless of when or where it was written. The motivation is a clean user model and encouraging the file system as a shared system-wide store for things like print spoolers and mailers; concurrent sharing is still expected to be infrequent, so the algorithm is optimized for the no-sharing case. (Section 5, p. 9) [That the algorithm is optimized for the no-sharing case is now stated in the note's Nelson callout (distributed-file-systems.md, section Sprite DFS Access Pattern Analysis); the any-read-returns-latest guarantee and its motivation are not.]
- The consistency-vs-synchronization distinction the lecture omits entirely: Sprite provides *consistency* (each read returns the most up-to-date data) but not *correct synchronization*; it cannot ensure concurrent applications order their reads and writes sensibly. If order matters, applications must use file-locking system calls or other communication. Consistency "simply eliminates the network issues and reduces the problem to what it was on time-sharing systems". (Section 5, p. 9)
- The server is the centralized control point: each server guarantees consistency for files on its disks, clients deal only with the server (no client-client interaction), and the algorithm depends on the server being notified on every open and close so it can detect imminent concurrent write-sharing. This is what prohibits name caching; Section 8 quantifies the cost. (Section 5, pp. 9-10) [That the server must see every open and close to detect concurrent write-sharing, which prohibits name caching, is now stated in the note's Nelson callout (distributed-file-systems.md, section Sprite DFS from Analysis to Design); per-server responsibility and the absence of client-client interaction are not.]

### 5.1 Concurrent Write-Sharing
- Definition: a file is concurrently write-shared when it is open on multiple clients and at least one has it open for writing. Sprite disables client caching for such a file; all reads and writes go to the server. (Section 5.1, p. 10) [Disabling client caching and routing all accesses through the server is now stated in the note body (distributed-file-systems.md, section Sprite DFS from Analysis to Design); the definition (open on several clients, at least one for writing) is not.]
- The two server actions on detecting it during an open: (1) notify the single client (if any) that has the file open for writing to write all dirty blocks back ("There can be at most one such client"); (2) notify all clients that have the file open that it is no longer cacheable, so they drop its blocks and send future accesses to the server. The server's kernel then serializes accesses to its cache, giving a single-timeshared-machine result. (Section 5.1, p. 10) [Now stated in the note's Nelson callout (distributed-file-systems.md, section Sprite DFS from Analysis to Design), so not beyond the notes.]
- The scoping rules the lecture compresses: disabling is per file and only while concurrent write-sharing holds; a file can be cached by many clients as long as none writes, and a single writer may cache it as long as there are no concurrent readers or writers elsewhere. When a file becomes non-cacheable only currently-open clients are notified; clients that merely hold stale blocks take consistency action at their next open. A non-cacheable file becomes cacheable again once concurrent write-sharing ends, but "for simplicity, Sprite does not ... re-enable caching for files that are already open". This contradicts the lecture's "when a writer closes, the server makes it cacheable again": in the lecture's scenario the remaining writer still has the file open, so in the paper it would not resume caching until it closes and reopens the file; caching is re-enabled only for later opens. (Section 5.1, pp. 10-11) [Per-file disabling only while sharing is concurrent, notifying only currently-open clients, and not re-enabling caching for already-open files are now stated in the note's Nelson callout (distributed-file-systems.md, section Sprite DFS from Analysis to Design) and the note's Nelson callout (distributed-file-systems.md, section File Access Operations in Sprite); the many-readers / single-writer caching conditions are not.]

### 5.2 Sequential Write-Sharing
- Definition: a file modified by one client, closed, then opened by another. The paper identifies *two separate problems with two separate mechanisms*, which the lecture tends to merge. (Section 5.2, p. 11) [The two-problems, two-mechanisms split is now stated in the note's Nelson callout (distributed-file-systems.md, section File Access Operations in Sprite); the definition is not.]
- Problem one, stale blocks in the opener's own cache, solved by version numbers: the server keeps a version number per file and increments it each time the file is opened for writing; each client stores the version of every file it caches and, on open, compares against the server's version and flushes its cached copy if they differ. The paper notes this is similar to NFS and early Andrew. (Section 5.2, p. 11) [Now stated in the note's Nelson callout (distributed-file-systems.md, section File Access Operations in Sprite), except the remark that this is similar to NFS and early Andrew.]
- Problem two, current data still sitting in another client's cache (the last writer need not have flushed on close), solved by last-writer tracking: the server records the last writer for each file and, on a new open by a different client, tells that last writer (if any, and if different from the opener) to write its dirty blocks through, and waits, before the opener reads. (Section 5.2, pp. 11-12) [Now stated in the note's Nelson callout (distributed-file-systems.md, section File Access Operations in Sprite), so not beyond the notes.]

### 5.3 Simulation Results
- Methodology: the BSD trace (3-day mid-week intervals on three VAX-11/780s running 4.2 BSD for program development, text processing, and CAD [OUST85]) was fed to a simulator that treated each timesharing user as a separate client workstation in a network with one file server. The trace drives this simulation and, again, the Section 7 estimate of per-user I/O rates for sizing a Sprite server; the lecture presents the trace as a direct study of Sprite. (Section 5.3, pp. 11-12) [The BSD trace on three VAX-11/780s, the one-client-per-timesharing-user simulation, and the Section 7 reuse are now stated in the note's Nelson callout (distributed-file-systems.md, section Sprite DFS Access Pattern Analysis); the 3-day intervals, workloads, and single-server network are not.]
- Table 1 (with consistency) numbers the lecture never gives: with no client cache, server traffic is 445,815 blocks read + 172,546 written = 618,361 total (100% traffic ratio). A 0.5-MB client cache drops the ratio to 32%, 1 MB to 29%, 2 MB to 28%, and it is essentially flat (28%) at 4 and 8 MB. So client caching cut server traffic by over 70% and gave read hit ratios over 80%. Of the write traffic, 4041 blocks were written through because of concurrent write-sharing and 6887 were flushed back because of sequential write-sharing. (Section 5.3, Table 1, p. 11) [The 4041 and 6887 write-sharing block counts are now stated in the note's Nelson callout (distributed-file-systems.md, section Sprite DFS Access Pattern Analysis); the traffic ratios and totals are not.]
- Table 2 (consistency ignored) is the counterfactual the lecture omits: the same simulation with no attempt to guarantee consistency drops the 0.5-MB ratio to 28% and the 8-MB ratio to 21%. Comparing the bottom-right entries of Tables 1 and 2 shows about one-fourth of all server traffic in Table 1 is due to cache consistency. Table 2 is "not realistic" (it would produce incorrect results) but gives an upper bound on what a cleverer consistency mechanism could save. (Section 5.3, Table 2, pp. 12-13) [The one-fourth consistency share of server traffic is now stated in the note's Nelson callout (distributed-file-systems.md, section Sprite DFS Access Pattern Analysis); the Table 2 ratios and the upper-bound reading are not.]

## Section 6: Virtual Memory and the File System
This entire section is absent from the lecture except for the one callout the note now carries.

- The goal: let each client cache be as large as possible (an application with small VM needs should be able to use most of physical memory as file cache), unlike UNIX's fixed-size caches, which would starve either large caches or large-VM applications. Sprite lets each file cache grow and shrink dynamically by having the file system and virtual memory modules *negotiate* over physical memory. (Section 6, p. 13) [That the file cache grows and shrinks by negotiating with virtual memory, up to most of a client's memory, is now stated in the note's Nelson callout (distributed-file-systems.md, section Sprite Distributed File System); the contrast with UNIX's fixed-size caches is not.]
- The mechanism: the file-system module and the VM module each manage a separate pool of physical pages. VM keeps its pages in approximate LRU order via a clock algorithm [NELS86]; the file system keeps cache blocks in *perfect* LRU order because all block accesses go through `read`/`write`. Each module records a time-of-last-access per page/block. When either module needs memory (a page fault, or a file-cache miss) it compares the age of its oldest page with the other module's oldest page; if the other module owns the older page it is forced to give it up, otherwise the module recycles its own oldest page. (Section 6, pp. 13-14) [Separate page pools and the oldest-page age comparison are now stated in the note's Nelson callout (distributed-file-systems.md, section Sprite Distributed File System); clock versus perfect LRU and the give-up/recycle rule are not.]
- The two problems with this scheme and their fixes. Double-caching: VM is itself a file-system user (backing storage is ordinary files; read-only code is demand-loaded from executables), so a naive design would land pages in both the file cache and the VM page pool, or move evicted VM pages into the file cache to age another 30 s. Fix: VM bypasses the local file cache when reading/writing backing files; for demand-loaded code already in the file cache (e.g. just recompiled), the page is copied to the VM pool and the file-cache block is given an "infinite" age so it is replaced first. (Section 6, p. 14)
- A consequence worth noting: although VM bypasses the *local* file cache for backing files, those backing files are still cached on servers, which "makes servers' memories into an extended main memory for their clients". (Section 6, p. 14)
- The second problem, multi-block pages: when a VM page holds several file blocks (the Sun-3 implementation has 8-KB pages but 4-KB blocks), what is the page's LRU age and what happens to the other blocks when the page is relinquished? Sprite's simple solution: a page's age is the age of its *youngest* block, and when a page is relinquished all its blocks are removed. The authors note they are still investigating this policy's effect. (Section 6, pp. 14-15)
- Two centralized alternatives the authors considered and rejected. (1) Access everything through VM by memory-mapping files, as in Apollo's DOMAIN [LEACH83], eliminating the file cache and letting standard page replacement balance memory; rejected mainly because a mapped-file approach must cache a file's pages before access, so consistency could not be implemented by refusing to cache shared files. (2) A centralized physical-memory manager serving both subsystems; rejected because the most logical way to compute page ages differs between VM and files, and the distributed scheme keeps only the shared notions (page age, LRU) while letting each module age pages its own way and even adjust relative aging rates. (Section 6, p. 15)
- The initial-experience tuning note: VM pages should get preferential treatment under memory contention, because the sequential nature of file access means a low file hit ratio hurts far less than a low VM hit ratio. (Section 6, pp. 15-16)

## Section 7: Benchmarks
- The five measurement questions the benchmarks target: how much faster file-intensive programs run with client caches; how much client caches cut server CPU load; how much they cut network load; how many clients a server/network can support; and how the benefits scale with CPU speed and memory. (Section 7, p. 16)
- The measurement configuration: Sun-3 workstations (~2 MIPS); clients were Sun-3/75 and Sun-3/160 with at least 8 MB; the server was a Sun-3/180 with 12 MB and a 400-MB Fujitsu Eagle disk. (Section 7, pp. 16-17)

### 7.1 Micro-benchmarks
- Table 3, the name-lookup cost study the lecture does not carry: three operations that each must contact the server, timed on a single-component pathname. Open/Close: 2.17 ms local disk vs 8.11 ms diskless elapsed (3.75 ms of it server CPU). Failed Open: 1.48 ms vs 4.13 ms (2.01 ms server). Get Attributes ("stat"): 1.28 ms vs 4.47 ms (2.12 ms server). Remote versions took 3-4 times as long as local, and about half the remote elapsed time was spent in the server CPU. (Section 7.1, Table 3, p. 17)
- Table 4, the raw sequential read/write throughput (KB/s) with accesses rigged to be satisfied in one place. Read: local cache 3269, server cache 475, local disk 224, server disk 212. Write: local cache 2893, server cache 380, local disk 197, server disk 176. (Section 7.1, Table 4, p. 17)
- The two results the paper draws from Table 4: a client reads its own cache 6-8 times faster than the server's cache, so client caching could in the best case make a program run 6-8x faster; and a client reads/writes the server cache at about local-disk speed. The current 2x server-cache advantage over local disk is an artifact of Sprite's disk layout (one block per disk revolution); the authors expect eventually to reach 4.3 BSD disk throughput (2-3x the Table 4 rates), after which local disk and server cache would be comparable, and as CPUs outpace disks the server cache should beat local disk up to network-bandwidth limits, suggesting a large server cache may beat a local disk even for paging. (Section 7.1, pp. 17-18)

### 7.2 Macro-benchmarks
- Methodology: well-known UNIX programs ported to Sprite, each run three times per data point and averaged. Table 5 lists six benchmarks with their I/O intensity (KB/s read, write): Andrew (copy a 70-file/200-KB directory tree, stat every file, read every byte, compile and link; Satyanarayanan's Andrew benchmark [HOWA87]) 54.9/34.4; Fs-make (recompile the Sprite file system, 33 files/33,800 lines of C) 56.6/28.9; Simulator (set-associative cache simulation from a 3375-KB address trace) 23.0/0.0; Sort (sort a 1-MB file) 47.0/90.2; Diff (compare two identical 1-MB files) 252.4/0; Nroff (format the paper itself) 16.1/18.1. The lecture names none of these benchmarks. (Section 7.2, Table 5, pp. 18-19)

#### 7.2.1 Application Speedups
- Table 6 gives per-benchmark elapsed times across three configurations (local disk; diskless server-cache-only; diskless client+server caches), each cold and warm, normalized to warm local-disk time. Without client caching, diskless machines were generally about 10-50% slower than those with disks; with client caching and a warm start the gap was very small, "in the worst case ... only about 12%". Figure 2(a) shows degradation falling as the client cache grows. The lecture gives neither the table nor the "10-50% / 12%" bracket. (Section 7.2.1, Table 6, Figure 2, pp. 19-21) [The 12% worst case matches the 0-12% figure now stated in the note's Nelson callout (distributed-file-systems.md, section Sprite Distributed File System); the table layout and the 10-50% uncached gap are not.]
- Two reasons the authors expect the client-caching advantage to grow over time: larger memories make larger (more effective) caches feasible, and processors are getting faster faster than networks or disks, so uncached workstations will increasingly wait on network/disk. (Section 7.2.1, pp. 21-22)

#### 7.2.2 Server Load
- Figure 3: a diskless client without a client cache used about 5-20% of the server CPU; with client caching this dropped by a factor of two or more, to 2-9%. The figure caption states the reduction as "a factor of 2-5". (Section 7.2.2, p. 22) [The factor-of-two-or-more reduction is now stated in the note's Nelson callout (distributed-file-systems.md, section Sprite Distributed File System); the 5-20% and 2-9% figures and the caption's factor of 2-5 are not.]

#### 7.2.3 Network Utilization
- The network-scaling argument the lecture omits: Lazowska et al. found network loading was not yet a major factor on Sun-2s [LAZO86], but it is becoming one as CPUs speed up. Without client caching the benchmarks averaged 6.5% utilization of the 10-Mbit/s Ethernet, with diff alone using 15% for a single client; a machine five times faster than a Sun-3 (SPUR, or the then-new Sun-4) would use 30-50% of the Ethernet running the benchmarks uncached. Client caching cut network utilization by about a factor of four, to an average of about 1.5%, which the authors judge enough to keep 10-Mbit Ethernet adequate for one or two more CPU generations. (Section 7.2.3, p. 23) [The factor-of-four reduction is now stated in the note's Nelson callout (distributed-file-systems.md, section Sprite Distributed File System); the utilization figures and the Ethernet-scaling argument are not.]

#### 7.2.4 Contention
- The multi-client experiment the lecture does not describe: several copies of Andrew (the most server-intensive benchmark) were run on different clients, each on its own copy of input/output files, so there was no cache-consistency overhead. Figure 4 shows the effect on client speed, server CPU, and network. With seven clients and no client caching, clients ran two-and-a-half times slower, the server was nearly 80% utilized, and the network over 30% utilized; with client caching and seven clients, each ran within 30% of local-disk speed, server utilization about 50%, network only 5%. (Section 7.2.4, pp. 23-25)
- The "50 clients" derivation in full: Figure 4 suggests one Sun-3 server supports at least ten Sun-3 clients running Andrew simultaneously; one Andrew instance is estimated to equal about 5-20 active users, so a server should support at least 50 users. The 5-20 figure rests on the BSD study's .5-1.8 KB/s per active user, scaled up 8-10x (to 4-18 KB/s) for paging traffic and faster machines (about 2x each), against Andrew's 90 KB/s average; it is cross-checked against Howard et al.'s "one Andrew instance ~= five average users" [HOWA87] and Lazowska et al.'s ~4 KB/s per user [LAZO86]. Server capacity should hold as CPU speeds rise if client and server speeds grow together, and be higher still when servers outpower clients. (Section 7.2.4, p. 25)

## Section 8: Comparison to Other Systems
- Table 7 compares Sprite with six systems (NFS, RFS, Andrew, Locus, Apollo, Cedar/CFS) on five parameters: cache location, cache size, writing policy, consistency guarantees, and cache validation. The lecture does not reproduce this table. Highlights: NFS (memory, fixed, on-close or 30-s delay, sequential, ask-server-on-open); RFS (memory, fixed, write-through, sequential+concurrent, ask-server-on-open); Andrew (disk, fixed, on-close, sequential, server-calls-client-when-modified); Locus (memory, fixed, on-close, sequential+concurrent, ask-server-on-open); Apollo (memory, variable, delayed-or-on-unlock, sequential, ask-server-when-lock); CFS/Cedar (disk, variable, on-SModel, consistency and validation both "not applicable", caches only immutable files); Sprite (memory, variable, 30-s delay, sequential+concurrent, ask-server-on-open). Apollo uses lock/unlock rather than open/close; CFS caches only immutable files; SModel is a tool for moving changed cached files back. (Section 8, Table 7, pp. 25-26)
- How the other write-sharing systems differ from Sprite: besides Sprite, only RFS and Locus support both sequential and concurrent write-sharing. RFS handles concurrent sharing like Sprite (disable caching) but is write-through and disables caching on the *first write* rather than at open. Locus supports concurrent write-sharing *without* disabling caching, using a read/write token-passing scheme where kernels pass tokens and flush caches to guarantee consistency. Apollo does not support concurrent write-sharing but offers lock/unlock primitives that readers and writers can use to serialize, with cache flushing that is correct if the primitives are used correctly. (Section 8, p. 26)
- The server-contact-on-open contrast and the Andrew callback history: every Table 7 system except Andrew checks with the server on open or lock to validate the cached copy. Andrew began with check-on-open too but was redesigned so servers track which clients cache which files and *notify* (call back) clients when a file is modified, letting clients open cached files without contacting the server and substantially cutting server load. Sprite deliberately processes all opens and naming on the server to avoid the complexity of client name caches. (Section 8, pp. 26-27) [Andrew's callbacks letting clients open cached files without contacting the server are now stated in the note's Nelson callout (distributed-file-systems.md, section Sprite DFS from Analysis to Design); the check-on-open survey and Andrew's redesign history are not.]
- Table 8, the "what if Sprite added name caching + callback" upper-bound estimate the lecture summarizes only loosely. Estimated by counting Open and Get-Attributes invocations and assuming all could be done on the client with no network/server involvement: Andrew benchmark degradation 12.5% -> 6.2%, server utilization 8.9% -> 5.6%, network utilization 1.04% -> 0.69%; Fs-make degradation 5.6% -> 1.0%, server 6.7% -> 4.1%, network 0.75% -> 0.45%. The conclusion: client-visible performance would improve only a few percent, but server and network utilization would fall by as much as one-third, potentially letting one server or network support 50% more clients. (Section 8, Table 8, pp. 27-28) [The conclusion (a few percent client-visible, up to one-third less server and network load, 50% more clients) is now stated in the note's Nelson callout (distributed-file-systems.md, section Sprite DFS from Analysis to Design); the estimation method and per-benchmark numbers are not.]
- Why Sprite's estimated callback gain is smaller than Andrew's measured gain: the authors attribute it to Andrew's servers being user-level processes (more portable, but remote operations much more expensive than in Sprite's kernel-level implementation); had Andrew's servers been in the kernel, there would have been less motivation to switch to callback. (Section 8, p. 28)
- Figure 5, the head-to-head the lecture does not quantify: Andrew-benchmark running time and server CPU utilization vs number of clients, for Sprite, Andrew, and NFS. The NFS/Andrew numbers come from [HOWA87] on Sun-3/50 clients; Sprite was measured on Sun-3/75s (about 30% faster) and renormalized for Sun-3/50 (elapsed x1.3, server utilization /1.3), and Sprite accessed binaries, paging, and temp files remotely whereas NFS/Andrew used local disks for them. (Section 8, pp. 28-29)
- The quantified comparison results: for a single client Sprite is about 30% faster than NFS and about 35% faster than Andrew, credited to Sprite's fast kernel-to-kernel RPC, delayed writes, and kernel (vs Andrew user-level) implementation. As clients increased, NFS saturated quickly; Andrew scaled best at about 2.4% server CPU per client vs Sprite's 5.4% and NFS's over 20%, Andrew's advantage attributed to callbacks. The paper restates that a Sprite server should support at least 50 clients, since NFS supports 10-20 and Sprite's server utilization is one-fourth of NFS's. (Section 8, pp. 29-30)

## Section 9: Future Work
This section is entirely outside the lecture.

- Two unresolved issues: crash recovery and disk overflow. (Section 9, p. 30)
- Crash recovery: the current system is fragile because of the state kept in each server's main memory; a server crash loses dirty cache blocks and open-file information, so client processes using that server's files usually have to be killed. By contrast NFS servers are stateless, which is less efficient (everything written through to disk) but lets clients sleep through a server crash and continue after reboot "with no ill effects". (Section 9, p. 30)
- The proposed recovery direction: make *server* caches write-through (client caches stay delayed-write), since even the most intensive benchmark generated server data at under 20 KB/s while a client can write a server disk at 176 KB/s (Table 4), so write-through at the server may cost little; combined with clients supplying enough information to re-open files after a crash, this aims for transparent continuation. (Section 9, pp. 30-31)
- Disk overflow: a client does not tell the server when it allocates new blocks, so a block written up to 30 s later may find no disk space, unlike UNIX where `write` reports a full disk immediately. The planned fix is a quota system: each client gets a block quota and requests more when it runs out; when free space is too low for quotas, clients must send explicit allocation requests on every new block. (Section 9, p. 31)

## Section 10: Conclusions
- The paper's own summary of what Sprite demonstrates: large caches give high-performance access to shared files; large client caches let diskless workstations match disk-equipped ones while using only a small share of server CPU; consistency is cheap because write-sharing is rare; dynamic cache sizing keeps file caches as large as possible without hurting VM. (Section 10, pp. 31-32)
- The buyer's-advice line the lecture never quotes: for anyone considering a local disk, "spend the same amount of money on additional memory instead", because more memory helps both file-system performance (larger cache) and virtual-memory performance, more than a local disk would. (Section 10, p. 32)

## Covered in the notes
- Sprite as a case study in cache consistency: all opens go through the server, clients cache blocks and keep a per-block dirty timer for the 30-second write-back, and the client/server state kept per file (client: cache yes/no, cached blocks, per-dirty-block timer, version; server: readers, writer, version).
- The 30-second delayed write-back: every 30 seconds a client writes back all blocks not modified in the last 30 seconds, and a file may be opened and closed several times before any data goes to the server.
- The "~33% of accesses are writes" figure and the inference that write-through is insufficient (the note frames the two-thirds number as improvable operations; the paper frames it as an upper bound on savings; see discrepancies).
- The open-duration statistics (75% of files open <0.5 s, 90% <10 s) and the deletion statistics (20-30% of new data deleted within 30 s, 50% within 5 min), used to reject write-on-close and justify delayed writes.
- That file write-sharing is rare, so the consistency algorithm is optimized for the no-sharing case.
- Concurrent write-sharing disables caching for the file and serializes accesses on the server; sequential write-sharing has the server collect dirty blocks from the previous writer.
- The use of per-file version numbers so client and server stay in sync across opens.
- That routing every open through the server means directories/names cannot be cached on the client.

## Notes vs paper discrepancies
Each item was checked against the paper text and, where relevant, a third-party source; sources are listed under "Discrepancy sources". Verdicts: LECTURE FRAMING (the note reproduces the lecture and the paper differs; keep the lecture version, annotate with a callout); NOTES WRONG (the note departs from both paper and lecture; fixed in place); NOT A REAL DISCREPANCY.

- The note attributes the access-pattern statistics to "a study ... [of] the production filesystem used by their department", implying Sprite's own file system was traced. The paper's Section 3 is explicit that the numbers are the "BSD study" [OUST85], a trace of three time-shared VAX-11/780s running 4.2 BSD, not Sprite; the paper uses the trace for Sprite in the Section 5.3 simulation and the Section 7 server-sizing estimate. Annotated with a callout under "Sprite DFS Access Pattern Analysis".
  - Verdict: LECTURE FRAMING. The lecture conflates the BSD trace with Sprite's own filesystem; the paper (Section 3, Section 5.3) and the later Baker et al. "Measurements of a Distributed File System" (SOSP 1991), which is the actual Sprite-trace study, confirm the distinction. The lecture wording is kept as exam-facing and the provenance is corrected in the callout.
- The note presents "66% of all operations can be improved" / the two-thirds figure as a count of improvable operations. The paper (Section 4.3) states it as a ceiling: because ~1/3 of accesses are writes, write-through "cannot reduce disk or server traffic by more than two-thirds". Annotated with a callout.
  - Verdict: LECTURE FRAMING. The arithmetic is the same; the paper's phrasing is an upper bound on savings, not a tally of operations. The callout records the paper's framing; the lecture's is kept.
- The note says the 30-second write-back interval is "directly related to" the 30-second deletion statistic. The paper (Section 4.3) adopts the interval as "similar to the one used in UNIX" (the UNIX 30-second sync convention) and says it plans to try *longer* intervals; the deletion statistics argue for a delay of several minutes, not 30 seconds specifically. Annotated with a callout.
  - Verdict: LECTURE FRAMING. The note draws a causal link the paper does not. The callout supplies the paper's actual derivation (UNIX convention, plus the 30-60 s client-to-server and server-to-disk timing); the lecture's mnemonic is left in place.
- The note treats sequential write-sharing as handled by one mechanism ("contact the old writer and gather dirty blocks"). The paper (Section 5.2) uses two distinct mechanisms for two distinct problems: version numbers for the opener's own stale blocks, last-writer flushing for data still in another client's cache. Annotated with a callout.
  - Verdict: NOT A REAL DISCREPANCY. The lecture is not wrong, only incomplete: its "gather dirty blocks" is the last-writer mechanism, and the version-number mechanism (which the note mentions separately in the state lists) is the other half. The callout joins them.
- The note says that when a writer closes a concurrently-shared file "the server will see it ... and will make the file cacheable again". The paper (Section 5.1) says a file becomes cacheable again once concurrent write-sharing ends, but "for simplicity, Sprite does not ... re-enable caching for files that are already open". Annotated with a callout.
  - Verdict: the paper contradicts the lecture on this step: the remaining writer still has the file open, and the paper does not re-enable caching for files that are already open. The lecture text is kept as the teaching version; the callout records the contradiction.
- The note frames routing every open through the server mainly as a consequence of the write-back design ("every open operation has to go to the server. This means directories cannot be cached"). The paper (Section 5, Section 8) frames server-contact-on-open as a deliberate choice tied to the consistency algorithm, with a quantified cost (Table 8: name caching + callback would save up to a third of server/network load). Annotated with a callout.
  - Verdict: NOT A REAL DISCREPANCY. Both are true and consistent; the paper adds the design-intent framing and the Table 8 cost estimate, which the callout supplies.
